One-sentence summary

Gopher is EAI Desktop as Layer 1: after install and one-click connect, a single full-screen app keeps admin on the left and your real harness (Layer 2) nested on the right, while Gofer and /eai work on a project folder (Layer 3) — same shell pattern as DesignEx, but the right pane is the tool, not the prototype.

DesignEx recap (the pattern we borrow)

DesignEx is not a new AI. It is a Mac app that wraps the coding agent you already pay for (Claude Code, Codex, Cursor) and adds product UI around it.

┌─────────────────────────────────────────────┐ │ 1. DesignEx app (Mac native) │ ← DesignEx owns this │ ┌─────────────┬─────────────────────┐ │ │ │ Left: Thread│ Right: Workbench │ │ │ │ (chat, forks)│ (HTML prototype) │ │ │ └──────┬──────┴─────────────────────┘ │ │ ▼ │ │ 2. Agent child process (Claude/Codex) │ ← Not DesignEx's AI │ ▼ │ │ 3. Files on disk (HTML, tokens, git) │ ← Agent output └─────────────────────────────────────────────┘

Key architectural idea: parent app spawns agent as child process (PTY or JSON-RPC over stdio). Parent owns left-side UX. Right side shows output, not a fake clone of Claude's UI.

Gopher three layers

DesignEx: shell → hidden agent → prototype on the right.
Gopher: shell → visible harness on the right → Gofer/work on disk.

LayerGopher nameWho owns it
1. Shell EAI Desktop — one window, two panes Enterprise AI (native app + WebView admin)

DesignEx right pane = output. Gopher right pane = the tool itself — an honest terminal view, not fake Claude chrome. We wrap the process; we do not skin their GUI.

Setup must not spawn a second window. The right pane activates in place — same geometry as install-5 two-column Setup, but the branding panel becomes the harness.

Data flow (one /eai session)

You (left or right) │ ▼ ┌─────────────┐ spawn / attach ┌──────────────────┐ │ EAI shell │ ───────────────────────►│ Claude Code PTY │ │ (Layer 1) │ cd project && claude │ (Layer 2) │ └─────────────┘ └────────┬─────────┘ │ │ │ context: project name, brief, │ /eai → Gofer MCP │ workflow id (when travel works) │ │ ▼ │ ┌──────────────────┐ │◄── left pane updates ────────────│ ~/…/kyc-onboard │ │ (admin, gates, credits) │ (Layer 3) │ └──────────────────────────────────└──────────────────┘
  1. Connect creates Layer 3 — folder + Gofer assets on disk.
  2. Right pane attaches Layer 2 — harness running in that project directory.
  3. User types /eai — Gopher ("go get that for me") runs Plan → Build → Deploy inside the harness.
  4. Left pane shows EAI product state (Plan stage first; builder/admin later) without killing the PTY session.

Critical rule (same as DesignEx / Codex App Server): left-pane navigation must not destroy the agent session. The PTY is owned by the main app process, not the WebView lifecycle.

Gopher vs DesignEx

DesignEx

Left: design thread (comments, forks). Right: rendered prototype (WebView). Agent hidden. Bet: own the design collaboration UX.

Gopher / EAI

Left: admin + builder (Plan, credits, processes). Right: the harness itself (terminal). Bet: own admin; harness stays theirs.

Same shell pattern — one window, two panes, child agent process. Different right pane: output vs tool.

Hard constraints

  • Cannot inject UI into someone else's harness when it is their standalone app. Embedding via PTY is wrapping the process, not skinning their GUI.
  • Two auth domains. EAI account (e.g. Microsoft Entra) and harness account (Anthropic, OpenAI) stay separate. UI must say so clearly.
  • VS Code / Cursor are not PTY CLIs. v1 either launches them externally with a detach path, or defers embed claims.
  • Web prototype limit. This repo can simulate layout and copy; it cannot prove real PTY behaviour. Native spike belongs in eai-installer.
  • Workflow travel browser → CLI is an open engineering question. Shell design assumes project name + brief + optional workflow id cross the panes; if CLI cannot consume it, left pane must show the gap honestly.
